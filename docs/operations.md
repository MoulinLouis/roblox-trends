# Production operations

The runbook of the production server. Commands run as `root` on the server (`ssh radar-prod`) unless they start with `ssh` or say otherwise. Everything the server runs is versioned in `ops/` (units, PostgreSQL configuration, shell scripts) and `scripts/`; change it through the repository, never by hand-editing a file that `ops/` manages. The phase 1b plan ([`docs/plans/2026-10-21-radar-v2-phase-1b-infrastructure.md`](plans/2026-10-21-radar-v2-phase-1b-infrastructure.md)) records how the server was built.

## 2. Access

### SSH

The owner's `~/.ssh/config` points both aliases at the Tailscale address, so Tailscale must be connected on the owner's machine (the Windows client also routes WSL):

```text
Host radar-prod
  HostName 100.103.240.76
  User root
  IdentityFile ~/.ssh/id_ed25519

Host radar-analysis
  HostName 100.103.240.76
  User analysis
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes
```

`ssh radar-prod` opens a root shell; `ssh radar-prod '<command>'` runs one command.

### Network

Only the tailnet reaches the server:

- ufw denies every inbound connection except on `tailscale0` and UDP 41641 (Tailscale direct connections). Public SSH (22/tcp) was removed after Tailscale access was proven, and the marker `/etc/radar/public-ssh-closed` keeps `provision.sh` from reopening it.
- A Hetzner Cloud Firewall in front of the server admits inbound UDP 41641 only, with no outbound rule (all outbound traffic allowed). Tailscale needs only outbound traffic; UDP 41641 lets peers connect directly instead of through a relay.
- sshd accepts keys only, and root only by key (`01-radar.conf`).
- PostgreSQL listens on localhost and its socket, and `pg_hba.conf` accepts socket connections only.

To check: `ufw status verbose`, `tailscale status`, `sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '`.

### Analysis sessions

The `analysis` user logs in with the owner's key and reaches PostgreSQL as `radar_analysis` by peer authentication: no password exists. The role is read-only (`default_transaction_read_only` and SELECT-only privileges), with a 5-minute `statement_timeout`, a 10-minute `idle_in_transaction_session_timeout` and at most 5 connections.

```bash
ssh radar-analysis 'psql -X -U radar_analysis -d radar -c "select count(*) from games"'
```

Scripts and tools on the owner's machine use a tunnel to the server's socket:

```bash
ssh -N -L 15432:/var/run/postgresql/.s.PGSQL.5432 radar-analysis
# then, in another terminal or tool:
psql postgresql://radar_analysis@localhost:15432/radar
```

The server sees a socket connection from the OS user `analysis`, so the same peer mapping applies and no password is asked.

`rising_games` computes the Radar page's metrics for any `as_of`. A session calls it with the values of `RADAR_CONFIG` in `src/lib/config.ts`:

```sql
select universe_id, name, ccu_avg, week_baseline, week_growth, week_growth_score, day_growth, is_event, samples, week_samples
from rising_games(as_of => now(), max_age_days => 30, min_ccu => 100, window_hours => 24, smoothing_ccu => 100,
  event_peak_ratio => 3, event_min_samples => 12, velocity_start => 100, velocity_middle => 1000, velocity_end => 10000,
  velocity_max_gap_hours => 2)
order by week_growth_score desc nulls last, ccu_avg desc limit 25;
```

### Dashboard

`https://radar-prod.tail6e77de.ts.net`, from any device of the tailnet. `tailscale serve --bg 3000` proxies HTTPS (a Tailscale certificate) to `127.0.0.1:3000`; the setting survives reboots. `tailscale serve status` prints it.

Pages, all in UTC:

- `/`, the Radar: games created within 14, 30 or 90 days, ranked by `rising_games`. Its `asOf` field replays a past hour.
- `/games/<universe id>`: the curves, the timeline, and the engagement, monetization and retention signals of one game.
- `/health`: what `radar status` and `radar system-check` report. Backups and the restore test report to Healthchecks only.

`radar-web` reads with its own sessions (`application_name` `radar-web` in `pg_stat_activity`): every transaction starts read-only (`default_transaction_read_only`), a statement gives up after 15 s and a lock wait after 5 s, and the pool holds at most 5 connections.

To view the pages locally against production without writing anything, open the analysis tunnel and run the development server on it:

```bash
ssh -N -L 15432:/var/run/postgresql/.s.PGSQL.5432 radar-analysis
# then, in another terminal:
DATABASE_URL=postgresql://radar_analysis@localhost:15432/radar npm run dev
```

## 3. Secrets inventory

Rules:

- The owner creates every credential and writes it on the server from their own terminal: `ssh radar-prod`, then `install -m 600 /dev/null <file> && nano <file>`.
- A secret never appears in a conversation with an AI session, in a printed file or on a logged command line. Inside the server shell, load a file with `set -a; . <file>; set +a`.

| File | Mode | Holds | Written by |
| --- | --- | --- | --- |
| `/etc/radar/radar.env` | `root:radar 640` | `DATABASE_URL` (peer authentication over the local socket, no password), `NEXT_TELEMETRY_DISABLED=1`; not a secret | `configure-database.sh` |
| `/etc/radar/healthchecks.env` | `root 600` | `HEALTHCHECKS_PING_BASE=https://hc-ping.com/<ping-key>` | owner |
| `/etc/radar/r2.env` | `root 600` | `R2_ENDPOINT` (the host only, `<account-id>.r2.cloudflarestorage.com`, with or without `https://`), `R2_BUCKET` (`radar-backups`), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | owner |
| `/etc/radar/pgbackrest-cipher` | `root 600` | The backup encryption passphrase | generated once by `configure-backups.sh`; restored by the owner on a rebuild |
| `/etc/radar/legacy.env` | `root 600` | `LEGACY_DATABASE_URL` (quoted, read-only Aiven role, no password) and `PGPASSWORD`; only for the v1 imports | owner |
| `/etc/radar/aiven-ca.pem` | `root 644` | The Aiven CA certificate (`sslmode=verify-full`); not a secret | owner |
| `/etc/radar/deploy.env` | `root` | Optional `RADAR_DEPLOY_BRANCH` (default `radar-v2`); absent until the cutover; not a secret | owner |
| `/etc/radar/public-ssh-closed` | `root` | Empty marker (section 2) | Task B2 |
| `/etc/pgbackrest/pgbackrest.conf` | `postgres 640` | The R2 keys and the cipher passphrase, copied from the two files above | `configure-backups.sh` |

The read-write Healthchecks API key is never stored on the server: it is used once per provisioning and deleted (section 8).

The owner's password manager holds what the repository and the server cannot give back:

- the R2 access key ID, secret access key, endpoint host and bucket name;
- the pgBackRest cipher passphrase (without it and the R2 keys, no backup can be restored);
- the Healthchecks ping key and read-write API key;
- the Aiven read-only password, until Aiven is deleted after the phase 4 cutover;
- the Hetzner, Tailscale, Cloudflare, Healthchecks.io and GitHub account credentials.

With them and this repository, a new server can be rebuilt and restored (section 6). The SSH key lives on the owner's machine; if it is lost, use the lockout recovery (section 9).

## 4. Everyday commands

```bash
radar status                               # per job: latest runs, degraded and failed counts, 429s, coverage, totals
systemctl list-timers 'radar-*'            # next and last start of every timer
journalctl -u 'radar-job@*' -f -o cat      # follow every job
journalctl -u radar-job@poll -n 100 -o cat # the last lines of one job
systemctl start radar-job@poll             # a manual run (add --no-block to return at once)
systemctl status radar-web                 # the dashboard; journalctl -u radar-web -o cat for its log
radar system-check                         # the system check, printed without pinging Healthchecks
```

`radar <script> [arguments]` runs an npm script of the live release as `radar` with `radar.env`. Run collection jobs through systemd (`systemctl start radar-job@<job>`), never `radar job <job>`: the unit never overlaps a run with the timer's, enforces the timeout and reports to Healthchecks.

Pause collection by disabling the six job timers, and resume by enabling them:

```bash
systemctl disable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
systemctl enable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
```

Stopping a timer is not enough: every deploy run (every 5 minutes) starts the job timers that are enabled, on purpose, so a deploy killed while the timers were paused for a migration heals on the next run. Disabling does not stop a running job; `systemctl list-units 'radar-job@*'` shows the ones still running. Pause the job checks in Healthchecks during a long pause (tags `job` and `quality`); a paused check resumes on its next ping.

## 5. Deployments

### How a commit is chosen

`radar-deploy.timer` runs `deploy.sh` every 5 minutes (`*:1/5:30`). One run:

1. Takes the lock `/run/radar-deploy.lock` (a second run exits at once), fetches root's mirror `/opt/radar/repo.git` and takes the head of the deploy branch: `radar-v2`, or `RADAR_DEPLOY_BRANCH` from `/etc/radar/deploy.env`. Only the head counts: intermediate commits are skipped.
2. Stops if the head is already live and marked `.deployed`, and fails if `/opt/radar/releases/<sha>.failed` exists.
3. Deploys only when the GitHub check run `validate` of that commit is completed with success. While CI runs or after it failed, the run logs it, pings `radar-deploy` as a success and deploys nothing; a GitHub or network outage is handled the same way.
4. Builds the release in `/opt/radar/releases/<sha>` at `nice 10`: `npm ci` and `npm run build` as `radar`. Root then takes the release back, replaces `ops/` with its own copy from the mirror and refuses a symbolic link at `.next` or `.next/cache`; only `.next/cache` is handed back to `radar`.
5. When `drizzle/` changed since the live release (or on the first deploy), stops the job timers and waits up to 5 minutes for running jobs. Runs `npm run db:migrate` as `radar`, up to 5 attempts 30 s apart.
6. Switches `/opt/radar/current`, copies `ops/systemd` into `/etc/systemd/system` and reloads systemd, links `/usr/local/bin/radar`, restarts `radar-web` when it is enabled and checks that it answers on `127.0.0.1:3000`.
7. Starts the enabled job timers, marks the release `.deployed`, prunes old releases (it keeps every release younger than 2 hours, the 3 newest older ones and the live one) and pings `radar-deploy`.

A deploy that stops after the switch is completed by the next run, since `.deployed` is written last.

```bash
journalctl -u radar-deploy -n 30 -o cat    # the latest runs
readlink /opt/radar/current                # the live commit
systemctl start radar-deploy               # a manual deploy now; waits for the end (add --no-block and follow the journal)
```

Prefer `systemctl start radar-deploy` to running `deploy.sh` by hand: only the unit loads `healthchecks.env` and pings the check.

### Rollback

The simplest rollback is a revert commit on `radar-v2`: CI and the next deploy run ship it within about 10 minutes. To switch back at once:

```bash
systemctl stop radar-deploy.timer            # first, or the next run redeploys the branch head within 5 minutes
systemctl is-active radar-deploy.service     # wait for "inactive" if a deploy was running
ls -lt /opt/radar/releases                   # the kept releases, newest first
ln -sfn /opt/radar/releases/<sha> /opt/radar/current.next && mv -T /opt/radar/current.next /opt/radar/current
cp -r /opt/radar/current/ops/systemd/. /etc/systemd/system/ && systemctl daemon-reload   # when the bad release changed ops/systemd
systemctl restart radar-web
```

Pause the `radar-deploy` check in Healthchecks while the timer is stopped. Migrations are forward only: the older release runs on the newer schema, which the compatibility rule below makes safe. Once a fix is pushed, `systemctl start radar-deploy.timer` (it is still enabled); the check resumes on the next ping.

### Failed build

`/opt/radar/releases/<sha>.failed` holds the build log, and every later run fails on that commit (pinging `/fail`) until a new commit arrives. Read it with `tail -n 50 /opt/radar/releases/<sha>.failed`. To retry the same commit after a transient failure (the npm registry, for example): `rm /opt/radar/releases/<sha>.failed && systemctl start radar-deploy`.

### Migration compatibility

A migration must stay compatible with the previous release, which may still be running a job (up to 30 minutes, or the legacy import) and which a rollback brings back:

- Add before you remove: new columns are nullable or have a default, and the code that needs them ships with or after them.
- Drop a column or a table one release after the code stopped using it; rename in two releases (add and copy, then drop).
- Migrations run with a 10-second `lock_timeout`, so one blocked behind a job fails and is retried (5 attempts, 30 s apart) instead of queueing every later query.

### What a deploy does not apply

- New units: copied, but not enabled. Enable a new timer with `systemctl enable --now <unit>`.
- Removed units: the file stays in `/etc/systemd/system`. Run `systemctl disable --now <unit>`, delete the file, then `systemctl daemon-reload`.
- `provision.sh` (packages, PostgreSQL configuration, sshd, firewall, system settings), `ops/postgresql/*.sql` (`configure-database.sh`) and the backup settings (`configure-backups.sh`): rerun the script from `/opt/radar/current/ops/bin` once the commit is live (section 8).
- Healthchecks periods and graces: `provision:healthchecks` (section 8).

## 6. Backups and recovery

### What runs

- pgBackRest archives WAL continuously to Cloudflare R2 (bucket `radar-backups`, path `/pgbackrest`, encrypted, asynchronous), at least one segment every 5 minutes while the database writes (`archive_timeout`).
- `radar-backup@diff` runs Monday to Saturday at 03:10 UTC, `radar-backup@full` on Sunday at 03:10. Each backup also runs `pgbackrest check` and `info`. Full backups are kept for 14 days, which gives point-in-time recovery over at least the last 14 days.
- `radar-restore-test` restores the latest backup every Sunday at 05:30 into a scratch cluster (`/var/lib/postgresql/radar-restore-test`, port 5499, archiving off), checks that it holds at least 95% of the production games and, once jobs have run, a job run less than 2 days old, then deletes it and logs `Restore test passed: …`. It needs free space for the data plus 8 GB, so it starts failing for lack of room around 55% disk use, an early warning before the system check's 70%.
- Hetzner's daily server backups are the second copy, for when the R2 repository itself is lost; restoring one loses everything after that day.

```bash
runuser -u postgres -- pgbackrest --stanza=radar info     # backups, WAL range, sizes
runuser -u postgres -- pgbackrest --stanza=radar check    # archiving works end to end
systemctl start radar-backup@diff                         # an extra backup
ls -lt /var/log/pgbackrest/                               # pgBackRest logs
```

### Point-in-time restore on this server

Everything written after the target is lost from the database (the WAL stays in the archive). The target is UTC, in the form `YYYY-MM-DD HH:MM:SS+00`; pgBackRest picks the newest backup that finished before it.

```bash
systemctl stop radar-deploy.timer radar-system-check.timer
systemctl disable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
systemctl list-units 'radar-job@*'                        # wait until no job runs
systemctl stop postgresql@18-main
runuser -u postgres -- pgbackrest --stanza=radar --delta --type=time --target='2026-10-22 14:00:00+00' --target-action=promote restore
systemctl start postgresql@18-main
runuser -u postgres -- psql -XAtc 'select pg_is_in_recovery()'   # f once the target is reached and the cluster promoted
systemctl start radar-backup@full                         # a first backup of the new timeline
systemctl enable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
systemctl start radar-deploy.timer radar-system-check.timer
```

Pause the Healthchecks checks for the duration.

### Rebuild on a new server

Power the old server off first: two servers must never archive into the same stanza.

1. **Owner**: in the Hetzner Console, create a CAX21 with Ubuntu 24.04, the owner's SSH key and backups, without the Cloud Firewall for now. In the Tailscale admin console, remove the old `radar-prod` machine so the new one can take the name.
2. From the owner's machine, over the new public address (root by key):
   ```bash
   ssh root@<public-ip> 'command -v git >/dev/null || apt-get install -y -q git; git clone --quiet --branch radar-v2 https://github.com/MoulinLouis/roblox-trends.git /root/radar-bootstrap'
   ssh root@<public-ip> /root/radar-bootstrap/ops/bin/provision.sh
   ```
3. Join the tailnet: `tailscale up --hostname=radar-prod` on the server prints a login URL; **Owner** approves the machine and disables its key expiry. Then `tailscale set --auto-update` and `tailscale ip -4`; point `HostName` of both SSH aliases at the new address and check `ssh radar-prod true` and `ssh radar-analysis true`. Close public SSH with `ufw delete allow 22/tcp && touch /etc/radar/public-ssh-closed`, and **Owner** applies the Cloud Firewall (inbound UDP 41641 only) to the new server.
4. **Owner** writes `/etc/radar/r2.env` and `/etc/radar/pgbackrest-cipher` from the password manager (`install -m 600 /dev/null <file> && nano <file>`).
5. Restore the database:
   ```bash
   /root/radar-bootstrap/ops/bin/configure-backups.sh --config-only
   systemctl stop postgresql@18-main
   runuser -u postgres -- pgbackrest --stanza=radar --delta restore
   systemctl start postgresql@18-main
   runuser -u postgres -- psql -XAtc 'select pg_is_in_recovery()'   # wait for f: the archive is replayed to its end
   ```
6. `/root/radar-bootstrap/ops/bin/configure-backups.sh` in full: its `stanza-create` is a no-op, then it turns archiving on and runs `pgbackrest check`.
7. `/root/radar-bootstrap/ops/bin/configure-database.sh`: writes `radar.env`; the roles already came back with the restore, and the grants are idempotent.
8. `/root/radar-bootstrap/ops/bin/deploy.sh`: clones the mirror, builds the branch head, runs any newer migration and installs the units. From now on, run the scripts from `/opt/radar/current/ops/bin`.
9. **Owner** writes `/etc/radar/healthchecks.env` (and `legacy.env` with `aiven-ca.pem` only if an import is still to come).
10. Enable everything:
    ```bash
    systemctl enable --now radar-web && tailscale serve --bg 3000
    systemctl enable --now radar-system-check.timer radar-deploy.timer radar-backup-full.timer radar-backup-diff.timer radar-restore-test.timer
    systemctl enable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
    systemctl start radar-backup@full
    ```

The Healthchecks checks live at Healthchecks.io and need no provisioning. The dashboard keeps its address once the machine has the name `radar-prod`.

## 7. Monitoring

Healthchecks alerts when a check misses its period plus grace, or when it receives a `/fail` ping. A job check's ping body holds the run's stats or error, and `radar-job-failed@` sends the last 40 journal lines; read them in the check's event log.

| Check | What the alert means | First commands |
| --- | --- | --- |
| `radar-<job>` | No completed run within the period plus the job's timeout and 5 minutes, or a failed run: an error the job reported (database, abandoned run), a unit killed at `TimeoutStartSec`, crashed or unable to start, or a timer that is disabled or stopped | `systemctl list-timers 'radar-*'`, `systemctl status radar-job@<job>`, `journalctl -u radar-job@<job> -n 100 -o cat`, `radar status` |
| `radar-<job>-quality` | No fully successful run for the job's interval plus an hour, while runs still complete degraded: 429s, a short, malformed or repeated Rolimon's list, too few games returned, stalled place resolution, failed promotions (README, quality gates) | `radar status` (degraded counts, watched stats, 429s, last error), `journalctl -u radar-job@<job> -n 100 -o cat` |
| `radar-deploy` | No deploy run for 35 minutes (the timer is stopped, or a run hangs), or a `/fail`: a failed build (and every run after it until a new commit), a failed export, migrations failing 5 times, a dashboard that does not answer after the switch (retried every run), an unexpected error. A red or pending CI is not an alert | `journalctl -u radar-deploy -n 50 -o cat`, `readlink /opt/radar/current`, `ls -lt /opt/radar/releases`, `tail -n 50 /opt/radar/releases/<sha>.failed` |
| `radar-system` | Disk above 70%; WAL archiving off, failing, or silent for 30 minutes (point-in-time recovery has stopped, and PostgreSQL keeps every unarchived segment, which fills the disk); a TimescaleDB policy paused or without success for 3 schedule intervals (at least 60 minutes); or the check could not run | `journalctl -u radar-system-check -n 20 -o cat`, `df -h /`, `runuser -u postgres -- pgbackrest --stanza=radar check`, the two queries below |
| `radar-backup` | A backup failed, or none succeeded for a day plus 3 hours | `journalctl -u 'radar-backup@*' -n 50 -o cat`, `runuser -u postgres -- pgbackrest --stanza=radar info`, `ls -lt /var/log/pgbackrest/`; retry with `systemctl start radar-backup@diff` |
| `radar-restore-test` | The weekly restore failed: not enough free disk, a restore or startup error, fewer than 95% of the games, or no recent job run in the restored copy | `journalctl -u radar-restore-test -n 50 -o cat`, `df -h /var/lib/postgresql`; retry with `systemctl start radar-restore-test` (it takes as long as a full restore) |

```bash
runuser -u postgres -- psql -X -c 'select archived_count, last_archived_wal, last_archived_time, failed_count, last_failed_wal, last_failed_time from pg_stat_archiver'
runuser -u postgres -- psql -X -d radar -c "select j.job_id, j.proc_name, j.hypertable_name, j.scheduled, s.last_run_status, s.last_successful_finish, s.next_start from timescaledb_information.jobs j left join timescaledb_information.job_stats s using (job_id) where j.job_id >= 1000 order by j.job_id"
```

A policy left paused (by an import, for example) resumes with `runuser -u postgres -- psql -X -d radar -c 'select alter_job(<job_id>, scheduled => true)'`.

### Games API limit

The game details endpoint, `GET games.roblox.com/v1/games?universeIds=…`, has a hidden per-IP limit that counts universe ids: about 500 per minute, measured on 2026-10-21 (README, verified API behavior). Its `x-ratelimit-*` headers do not show it, and the votes endpoint on the same host does not share it. `poll` reads it every 10 minutes with one request of 50 ids every 7 s: each run requests the hot set, the 2,000 highest-priority active games, then the 1,150 other active games whose details are the oldest, 63 requests in about 441 s. This tail rotates, each of its games refreshed every 20–30 minutes, while `census` still counts its CCU every 10 minutes. A game Roblox does not answer (moderated or deleted, for example) moves behind the other tail games like a polled one, so it is retried once per tail cycle; `missing` counts the requested games Roblox did not answer, and `missingSample` in `job_runs.stats` lists up to 10 of their universe ids. The promotions of `census`, `charts` and `explore` call it too, from their own processes, and spend the same budget. Each 429 multiplies the endpoint's spacing by 1.5 for the rest of the process, up to 30 s; the next run, a new process, starts again at 7 s.

A 429 storm in `radar status`:

- On the `poll` row, `degraded` and `rate-limited` grow, and `429s/requests` rises from about 0 to a few per run.
- The watched stats of the last completed run show `http.rateLimitedResponses` above 0 and `http.endpointIntervalMs={"games.roblox.com/v1/games":…}` above 7000 (10500, 15750, 23625, then 30000). With `rateLimited=true stoppedBy=error`, a 429 outlasted the retries and the rest of the requested games was skipped; with `stoppedBy=deadline`, the slower spacing ran out of time. Either way `skipped` counts the requested games left out, the end of the request order (tail before hot set), and `shedBelowCcu` is the priority of the first of them.
- `medianTailDetailsMinutes`, the median age of the details of the tail games requested (games Roblox did not answer left out), rises above its usual 20–30 minutes: the tail rotation falls behind.
- Coverage (Rolimon's places at or above 100 CCU polled within 60 minutes, which a tail game polled every 20–30 minutes still meets) falls below its usual share.

The journal (`journalctl -u radar-job@poll -n 100 -o cat`) shows `External service throttled or unavailable; retrying` with a `retryDelayMs` of about 30–60 s (the limit's reset), and one `Slowed down a rate-limited endpoint for the rest of the process` line per new spacing.

A 429 now and then needs nothing. When most runs slow down, check first whether another job's promotion ran during the poll run (census at +2:40 of each slot, charts at :16:30, explore at :26:30), then raise the 7 s of `EXTERNAL_REQUEST_CONFIG.minimumIntervalByEndpoint` in the repository and lower `JOB_CONFIG.poll.tailUniversesPerRun` (or `hotUniverses`) so the requested games still fit the deadline: `JOB_CONFIG.poll` holds the arithmetic.

## 8. Maintenance

Before any maintenance that restarts PostgreSQL, quiet the server and pause the Healthchecks checks:

```bash
systemctl stop radar-deploy.timer radar-system-check.timer
systemctl disable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
systemctl list-units 'radar-job@*'      # wait until no job runs
```

and afterwards:

```bash
systemctl enable --now radar-census.timer radar-poll.timer radar-votes.timer radar-charts.timer radar-explore.timer radar-thumbnails.timer
systemctl start radar-deploy.timer radar-system-check.timer
```

### Ubuntu

Unattended upgrades install Ubuntu security updates only, daily, and reboot automatically at 04:48 UTC when one needs it (between job starts: a reboot costs at most one poll slot). Every unit, the timers and `tailscale serve` come back by themselves. The log is `/var/log/unattended-upgrades/unattended-upgrades.log`; `/var/run/reboot-required` exists while a reboot is pending.

### PostgreSQL minor releases

PGDG is not an unattended-upgrades origin, because a PostgreSQL minor release once broke the TimescaleDB extension ABI. Apply a minor release by hand, once CI passes on the same minor version. The version CI runs, on the owner's machine:

```bash
docker run --rm --entrypoint postgres timescale/timescaledb:2.30.2-pg18 --version
```

On the server, with the job timers disabled as above:

```bash
apt-get update -q && apt-cache policy postgresql-18
apt-get install -y -q --only-upgrade postgresql-18 postgresql-client-18
systemctl restart postgresql@18-main
runuser -u postgres -- psql -XAtc 'show server_version'
systemctl start radar-system-check && journalctl -u radar-system-check -n 5 -o cat
```

pgBackRest comes from PGDG too: `apt-get install -y -q --only-upgrade pgbackrest`, outside the backup window, then `runuser -u postgres -- pgbackrest --stanza=radar check`. A blanket `apt-get upgrade` also upgrades PostgreSQL, and so does rerunning `provision.sh` (below): treat both like a minor release.

### TimescaleDB

A TimescaleDB upgrade is a change set of its own:

1. In the repository, bump the CI image `timescale/timescaledb:<version>-pg18` in `.github/workflows/ci.yml` and `timescaledb_version` in `ops/bin/provision.sh` together (`operations-scripts.test.ts` keeps them equal), and the version in the README. Check first that the package exists for arm64: `apt-get update -q && apt-cache madison timescaledb-2-postgresql-18` on the server. Push, and wait for CI and the deploy.
2. On the server, with the job timers disabled as above:
   ```bash
   /opt/radar/current/ops/bin/provision.sh     # installs and holds the new packages
   runuser -u postgres -- psql -X -d radar -c 'ALTER EXTENSION timescaledb UPDATE'
   systemctl restart postgresql@18-main        # loads the new loader of shared_preload_libraries
   runuser -u postgres -- psql -X -d radar -Atc "select extversion from pg_extension where extname = 'timescaledb'"
   systemctl start radar-backup@full
   ```
   `ALTER EXTENSION` must be the first command of a fresh session (`psql -X -c`), run as `postgres`, which owns the extension.

### Node.js

NodeSource is not an unattended-upgrades origin either. Within the major version: `apt-get install -y -q --only-upgrade nodejs`, then `systemctl restart radar-web`; jobs and builds pick it up at their next start. A new major version changes `node_major` in `provision.sh`, `.nvmrc` and the CI `node-version` together, then reruns `provision.sh`.

### Tailscale

Tailscale updates itself (`tailscale set --auto-update`). `tailscale version` shows the running version.

### Healthchecks checks

Rerun `provision:healthchecks` after any change of `JOB_CONFIG` or `HEALTHCHECKS_CONFIG`. It creates or updates every check by slug (removed checks must be deleted by hand in Healthchecks) and needs the read-write API key, which it reads from the environment only. From the repository on the owner's machine:

```bash
read -rs HEALTHCHECKS_API_KEY && export HEALTHCHECKS_API_KEY   # paste the key, then Enter
npm run provision:healthchecks
unset HEALTHCHECKS_API_KEY
```

Or on the server, after the owner wrote the key alone into `/root/healthchecks-api-key` (`install -m 600 /dev/null /root/healthchecks-api-key && nano /root/healthchecks-api-key`):

```bash
HEALTHCHECKS_API_KEY="$(cat /root/healthchecks-api-key)" radar provision:healthchecks; status=$?; shred -u /root/healthchecks-api-key; exit $status
```

Expected: 16 `Check created` or `Check updated` lines.

### Provisioning changes

Deploys do not apply `provision.sh`. Once a change to it is live, rerun `/opt/radar/current/ops/bin/provision.sh` with the job timers disabled: it restarts PostgreSQL when its configuration changed, and it upgrades PostgreSQL, Node.js, pgBackRest and Tailscale to their newest packages. Likewise rerun `configure-database.sh` after a change to `ops/postgresql/*.sql`, and `configure-backups.sh` after a change to the backup settings (it reloads PostgreSQL, or restarts it when archiving was off).

## 9. Lockout recovery

When SSH over Tailscale fails (Tailscale logged out, a broken sshd or ufw configuration, a lost key):

1. Hetzner Console → the server → Rescue tab → "Reset root password", then open the web console (Console button) and log in as `root` with that password. The password works only there: sshd refuses passwords.
2. Diagnose: `tailscale status`, `systemctl status tailscaled ssh`, `ufw status verbose`, `sshd -t`. `tailscale up --hostname=radar-prod` prints a login URL when the machine was logged out.
3. If public SSH is needed: `ufw allow 22/tcp` restores it in ufw, and **Owner** adds an inbound TCP 22 rule to the Hetzner Cloud Firewall; then `ssh root@157.90.125.226` works with the key. Close both again once Tailscale works: `ufw delete allow 22/tcp` and remove the firewall rule.
4. If the system does not boot: Rescue tab → enable the rescue system with the owner's key, power-cycle the server, open public SSH in the Cloud Firewall as above, `ssh root@157.90.125.226`, then mount the root partition (`lsblk` shows it) to repair it.
